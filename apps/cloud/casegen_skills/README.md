# 用例编写规范包

AI 生成测试用例时，除了固定的输出格式和自检规则，还会按模块读这里的规范包：领域规则、正反示例、额外的自检规则。
改完保存即生效，不用重启。

## 怎么生效

- `默认.md`（`modules: ["*"]`）对所有模块生效。
- 模块专属的包（如 `空调.md`，`modules: [HVAC]`）叠加在默认包后面：规则、示例、自检规则都是两份合在一起。
- 模块缩写见 `apps/cloud/modules.yaml`；一个模块只认第一份声明了它的包。
- 需求抽取时，只有已经认出是哪份 PRD（飞书文档已绑定、或标题匹配到已有 PRD）才用模块包的“抽取”规则，否则只用默认包。

## 文件格式

```markdown
---
name: 空调
modules: [HVAC]
version: 2            # 改了规则就加 1
checks:               # 额外自检：确定性检查，不调模型；命中后用例带“规范”提示，审核台可见
  - {field: expect_tts, forbid: "^(好的|已执行)[。！!]?$", msg: 期望播报只写了“好的”, suggest: 修改, scope: voice}
  - {field: expect_screen, require: "℃|档", msg: 期望屏幕没写温度或档位}
---
## 抽取
（追加到需求抽取的提示词）
## 编写
（追加到用例生成的提示词）
## 示例
（正反示例，追加到用例生成的提示词）
```

- `field`：title / precondition / steps / expected / utterance / expect_screen / expect_tts / page
- `forbid`：命中这个正则就提示；`require`：没命中就提示（二选一或都写）
- `suggest`：修改 / 驳回 / 确认 / 转需求方；`scope`：all / voice（只查语音用例）/ ui（只查非语音用例）
- 每节最多 3000 字。写错的规则会被跳过，原因在 `GET /api/casegen/skills` 的 `problems` 里。

## 怎么判断改得好不好

每个批次记下用的规范（名称、版本、内容哈希）。`GET /api/casegen/skills` 按规范版本统计审核结论：
通过 / 修改 / 驳回 / 转需求方的条数、通过率、最常见的驳回原因。改规范前后对比通过率，驳回原因多的地方补规则或示例。

保存前也可以先在网页 `/skills` 的编辑页里看：

- **试生成**：同一组需求点用已保存的规范和草稿各生成一次，并排对比用例和自检标记（不入库，调 2 次模型）。
- **建议**：根据本模块被驳回 / 修改的用例，让模型提出规则补充和自检规则，并算出每条自检规则能拦住几条驳回、误伤几条已通过用例。只是建议，勾选加入草稿后人工确认再保存。
